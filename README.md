# EgWalker (Swift)

A pure-Swift implementation of **Eg-walker**, the collaborative text editing algorithm from
*"Collaborative Text Editing with Eg-walker: Better, Faster, Smaller"* (Joseph Gentle, Martin
Kleppmann, EuroSys 2025).

- **Zero dependencies, no Rust toolchain, no XCFramework.** Plain SwiftPM.
- **Byte-identical to diamond-types** (the Rust reference implementation) on the conformance
  suite, real git histories and all seven paper traces.
- **Fast:** faster than diamond-types on sequential and lightly concurrent histories, on par
  on heavily branched ones, with a fraction of the peak memory on concurrent traces
  (see [Benchmarks](#benchmarks)).

> Status: research-grade library, built in a day as a learning project. The core merge
> algorithm is heavily tested; the public API is small and will change.
> Documentation: [docs/](docs/README.md): concepts, API guide, architecture, testing,
> performance, design decisions and roadmap.

## Usage

```swift
import EgWalker

var alice = OpLog(), bob = OpLog()
alice.insert(agent: "alice", at: 0, "Hello")
bob.merge(from: alice)

alice.insert(agent: "alice", at: 5, " world")   // concurrently...
bob.insert(agent: "bob", at: 0, "Oh, ")          // ...on two replicas

alice.merge(from: bob)
bob.merge(from: alice)
assert(alice.checkout().text == bob.checkout().text)  // "Oh, Hello world"
```

Positions count Unicode scalars, not UTF-16 units. See the [API guide](docs/api-guide.md) for
syncing, open documents, preconditions and UIKit/AppKit offset conversion.

`OpLog` is the only state you need to persist or sync. `checkout()` replays it into text;
`checkoutDocument()` does the same without materialising a `String`. For an open document,
`TextDocument.merge(oplog)` applies only what's new, revisiting just the concurrent events:

```swift
let doc = alice.checkoutDocument()
// ... more events arrive in `alice` via merge(from:) ...
doc.merge(alice)
```

## How it works (short version)

1. Events are stored with plain integer positions, like OT, in a run-length-encoded causal
   graph.
2. Events that nothing can be concurrent with (*critical* events) are applied directly to the
   text: no CRDT at all. Sequential editing never builds CRDT state.
3. Between critical events, a temporary CRDT (YjsMod/Fugue items in an arena-allocated
   B-tree) transforms concurrent operations. It is discarded at the next critical event.
4. Large concurrent regions are replayed depth-first, smallest subtree first, which halves the
   retreat/advance work on branchy histories.

Details: [Concepts](docs/concepts.md), [Architecture](docs/architecture.md), and the
[optimisation log](docs/performance.md#optimisation-log), including the experiments that did
*not* work.

## Testing

```bash
swift test                                  # full suite (~80 s in debug)
EGWALKER_FUZZ_ITERS=20000 swift test --filter Fuzz   # soak fuzzing
swift test --sanitize=address               # unsafe-pointer code under ASan
Scripts/mutate.py --limit 160               # mutation testing (see Benchmarks/mutation)
```

- **Conformance:** 1,000 histories generated by diamond-types, with full B-tree invariant
  validation after every step.
- **Differential fuzzing:** random multi-replica sessions (incl. emoji and combining
  characters). The optimized engine must match a line-by-line port of the TypeScript
  reference implementation, replicas must converge, and both traversal orders must agree.
- **Real histories:** git imports of nodejs and git, plus the paper's S1–A2 traces exported
  with their original agent names.
- **Mutation testing:** a small project-specific runner (`Scripts/mutate.py`) checks that the
  suite actually notices plausible bugs. 110 sampled mutants: 84.5% killed on the first run;
  after triage, 4 new tests and debug bounds asserts, 90% killed and every remaining survivor is equivalent,
  metrics-only or performance-only ([triage](Benchmarks/mutation/TRIAGE.md)).
- **AddressSanitizer:** the full suite runs clean under ASan.

## Benchmarks

`Scripts/fetch-traces.sh` downloads the paper traces and diamond-types; `Scripts/bench.sh`
runs both implementations interleaved on the same machine. Time is `checkout` of an
already-loaded oplog (the paper's "merge" benchmark); heap is the peak heap growth during one
checkout, measured with the same malloc tracker for both.

Intel Xeon @ 2.1 GHz, Linux, 2 vCPUs (full output: [Benchmarks/results/RESULTS.md](Benchmarks/results/RESULTS.md)):

| Trace | Ops | Swift | diamond-types | Speed-up | Peak heap Swift | Peak heap Rust |
|---|---|---|---|---|---|---|
| S1 | 779k | 1.98 ms | 4.05 ms | 2.05x | 0.33 MB | 1.39 MB |
| S2 | 1.1M | 3.50 ms | 6.04 ms | 1.73x | 0.41 MB | 0.88 MB |
| S3 | 2.3M | 5.49 ms | 8.21 ms | 1.50x | 1.17 MB | 0.86 MB |
| C1 | 652k | 74.6 ms | 105.1 ms | 1.41x | 1.14 MB | 42.7 MB |
| C2 | 608k | 107.3 ms | 153.6 ms | 1.43x | 1.63 MB | 50.4 MB |
| A1 | 947k | 21.7 ms | 18.8 ms | 0.87x | 3.02 MB | 3.16 MB |
| A2 | 698k | 53.8 ms | 50.5 ms | 0.94x | 6.99 MB | 5.83 MB |

Swift wins on sequential (S) and moderately concurrent (C) histories; diamond-types is still
6–13% faster on the heavily branched A traces. Release builds keep Swift's bounds and overflow
checks on. Numbers on Apple Silicon have not been measured yet.
